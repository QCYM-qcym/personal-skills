# 课程工作区、自适应教学与代码库入门

在初始化课程、设计正式课件、跨会话定做下一课或带新人理解代码库时读取。

## 1. 学习工作区

新课程在用户指定的课程根目录采用以下结构；已有课程保留旧路径，按职责映射，不为了统一名字搬动或覆盖用户文件。

```text
课程目录/
├─ mission.md             目标、范围、前置、时间与验收
├─ resources/             教材/文档或来源链接；index.md 记版本与已读范围
├─ lessons/               001-topic.html 等正式教学单元
├─ glossary/              术语、概念卡与它们的联系
├─ solve-cards/           解题/解决问题卡，建立在已经理解的基础上
├─ notes.md               用户问题、理解变化、课次索引与接续摘要
├─ maps/                  已有四图与跨模块联系，按需创建
├─ assets/                课件样式、图像等共用资源，按需创建
└─ .learning/             既有状态协议中的 CURRENT、NODES、REVIEWS 与事件等
```

`mission.md` 是用户可读的任务定义，`resources/index.md` 是材料索引，`glossary/` 复用概念卡，不另复制一套概念正文。`notes.md` 只记录简短理解变化及指向卡片/证据的链接；其接续区标当前 revision，并链接 CURRENT。notes 与状态冲突时，能力与当前活动以已提交状态为准，用户明确更正另记事件。

新目录中的 `.learning/MISSION.md` 和 `.learning/RESOURCES.md` 仅分别指向 `../mission.md` 与 `../resources/index.md`，不维护两份目标或来源全文。每次读取时跟随这些明确的指针；旧目录的同名文件已存正文时继续作为唯一依据，课程首页可反向链接。按状态协议保存目标变化事件，不能只改展示摘要。

Solve card 使用 [解决问题卡模板](../templates/solve-card.md)：提炼问题结构、适用条件、选择方法的理由、关键步骤与验证，保留真实首错；不编成待练原题的答案库。基础学习阶段可以建立问题卡但方法先留待探索，概念通过后再集中总结。

## 2. 为什么正式课程用 HTML

HTML 用于需要交互的教学单元：可操作的参数与结果对照、分步图解、逐级提示、选择/输入测验和针对错误的反馈。这些行为可以在同一个页面中明确控制；普通 Markdown 主要负责可检索、可链接的知识与记录，某些宿主的 Markdown 扩展也能交互，但能力并不统一。

正式课默认保存在 lessons/ 下，HTML 不是把 Markdown 换扩展名。每课包含：一个可检验目标、前置与诊断依据、连贯讲解、一个有理由的示例、必要的图解、独立任务、按需提示/反馈、来源及下一步。按 [课件设计模板](../templates/lesson-design.md) 生成；只加入能帮助当前概念的交互，不为装饰拖慢教学。

要求：

- 图解说明结构/过程/条件，具有文字替代说明；交互有键盘操作和清晰标签，适合平板宽度。
- 待练原题答案默认隐藏；用户主动提交后可给反馈，完整解答仅主动展开。提示与完整解答的查看情况需要进入作答证据；前端隐藏不是防作弊机制。
- 测验必须有合理判定与反馈；开放式解释交给 agent 检查，不能用关键词命中宣称理解。页面完成和得分不自动等于掌握。
- 页面可提供“复制本轮结果”：课次、题目 ID、用户输入、使用提示/展开答案、结果及时间。用户带回后 agent 区分自述和可检查证据，再更新课程状态；HTML 默认没有跨应用写文件能力，不声称自动同步 `.learning/`。
- 优先可离线打开的资源。确需网络依赖时说明；浏览器打不开或工具不支持文件生成时用对话/Markdown 交付同样的教学内容，标明降级，不中断学习。
- 生成后实际打开检查布局、图解、题目交互、反馈和提示控制；无法运行或视觉检查时明确未验证项，不能声称测试通过。

华为笔记承接从课件提取的无答案手写学习页；HTML 交互在浏览器中使用，导出 PDF 是静态版本，不承诺在华为笔记里保留交互。Obsidian 负责连接课程、概念和手写附件。

## 3. 最近发展区：用证据调难度

目标是让用户借助有限支架能够推进，并逐渐撤去帮助。它不是可由一次测验精确测量的固定区间，也不是强制维持某个正确率。结合用户的实际尝试、提示量、解释质量及“太简单/太难”的反馈持续校准。

| 观察 | 下一步 |
| --- | --- |
| 能独立解释和完成，觉得重复 | 减少支架；只增加一个变化维度，如情境、约束或表示 |
| 首次有卡点，但一个提示后能解释并继续 | 暂留该难度，换同结构变式，逐渐撤提示 |
| 连续卡在同一前置、提示升级仍无进展或明显受挫 | 缩小任务，补完整示例/前置；换表示，再给可完成的小任务 |
| 没有作答证据，只有“看完了” | 给一个低负担诊断，不直接升难或整课重教 |

每次只调整任务复杂度、前置负担、表示方式或支架中的一个主要变量。时间长可能来自书写或设备操作，不能直接判为能力不足；询问卡点而不做心理诊断。用户可以选择更难挑战或暂时跳过，保留真实能力标记。

在个人设置或 notes 的课程计划区记录当前难度假设与支架策略，CURRENT 保存具体下一题，NODES 只存已证实的能力。新证据可以推翻难度假设，不把“最近发展区”变成固定标签。

## 4. 跨会话：进度报告 → 诊断 → 下一课

用户说“我学到哪里、哪里不懂”时：先读既有状态、最近课次和相关作答，再将其自述与证据对齐。无状态时，最少收集学到的内容、一次尝试/卡点、当前目标与可用时间；不假装知道历史。

通常用一个短任务检验关键前置；已有足够新鲜的证据时直接诊断，不重复考试。输出“已能独立做什么、尚缺什么、下一课为何这样安排”，随后生成或调整一个 lessons/HTML 单元，而不是预先批量生成整学期。

下一课只针对当前缺口，安排目标、支架、练习和退出标准；记入状态的唯一下一步与 notes 的课次索引。用户尚未回答诊断时，课件可给有标注的临时路径，不把定做计划当作已掌握事实。旧课已使用时保存其版本，新课递增编号；修订旧课保留原作答关联。

## 5. 工程视角：带新人理解代码库

将课程目标定为可观察的工作能力，例如“从一个请求入口追踪到数据写入，并独立验证一个小改动”。先读仓库 AGENTS、README、领域词汇、架构/ADR、实际入口和测试约定；确认分支/提交，讲解引用真实文件与符号，不虚构调用关系。

采用一条真实行为贯穿学习：

1. 全景：产品解决什么问题、模块边界与外部依赖。
2. 术语：glossary 记录领域概念及代码中的对应名称。
3. 路径：入口 → 核心逻辑 → 数据/外部系统 → 用户可见结果，标真实文件与不确定部分。
4. 诊断：让新人找一个入口、预测一处行为或解释一段数据流，据此判断需要补语言基础还是领域模型。
5. 定做一课：给一条路径的交互图解和小练习，不按目录逐个文件灌输。
6. 验证：新人独立追踪相邻路径、定位一个问题，或在用户已授权的隔离环境中完成小改动并解释测试结果。

solve-cards 保存“症状/需求 → 关键路径与假设 → 验证方法 → 已证实结论”，notes 保存误解与待确认问题。只读讲解不自动授权修改生产环境、运行未知脚本、部署或提交代码。agent 代做的改动不能计为新人掌握；执行受限时区分已读推断与实际运行结果。
